# 天气提前提醒：设计、接口与专项测试

## 功能与数据来源

复用系统设置中已有的和风天气凭据，不要求用户输入经纬度。城市从已启用的猪猪组件、家庭记忆或未来7天内有明确日期的计划取得；模型提取的城市必须能在对应原文找到依据，同名地点不明确时不猜测。

采用和风天气新版接口：

| 数据 | 请求范围 | 更新频率 | 官方文档 |
|---|---|---|---|
| 逐日预报 | 今天加随后7天，共8天 | 每小时 | [Daily Forecast](https://dev.qweather.com/en/docs/api/weather/weather-daily-forecast/) |
| 逐小时预报 | 未来48小时 | 每小时 | [Hourly Forecast](https://dev.qweather.com/en/docs/api/weather/weather-hourly-forecast/) |
| 官方气象预警 | 当前有效及更新、解除消息 | 每5分钟 | [Weather Alert](https://dev.qweather.com/en/docs/api/warning/weather-alert/) |

新版预警保留发布单位、等级颜色、发布时间、生效/预期开始/结束时间、更新替代关系和官方防范建议。没有通过温度阈值“生成官方警报”；系统算出的降温、降雨、大风候选明确标为预报风险。和风天气旧 `/v7/warning/now` 已列入[弃用列表](https://dev.qweather.com/en/docs/deprecated/)，新增功能不依赖该接口。

每类数据独立带 `status`、`fetchedAt`、`items`、`attributions`。只有 `fresh` 且预警数组为空才表示本次查询成功、暂无有效预警。网络失败或额度不足返回 `stale/unavailable`，不会解释成安全。聊天等待外部天气最多2.5秒，未及时返回时说明缺失；后台继续通过共享请求和缓存补齐。

## 自动提醒流程

1. 后台每分钟检查已开启天气提醒的组件。家庭记忆或近期计划改变后，在下一轮重新提取明确城市；不改变原始记忆、计划或组件配置。
2. 汇总组件城市和提取的城市，最多8处。相同实际地点的来源缓存复用；每个城市的预报、逐小时数据和官方预警独立刷新。
3. 生成候选：相邻日最高温预报下降达到组件温差；逐小时降水概率至少60%且降水量至少0.5mm；风速或阵风达到10.8m/s；以及有效官方预警。这些阈值只产生候选，不直接广播。
4. GLM/DeepSeek获得家庭全文、计划、天气和候选，判断具体关联，给出原文依据、建议、开始时间和结束时间。用户的日常出门时窗、工作日设置一并提供。无关联应返回空列表。
5. 服务端再核验候选编号、城市与记忆/计划的归属、原文依据、计划日期、提醒时间。一般预报最早提前24小时，旅行预报最早提前72小时；官方预警可以在发布后提醒。计划不在预报覆盖期时不外推未来天气。
6. 通过已有 `briefing` 任务领取与播放回执链路投递字幕和可选语音。模型可选择临近出门再提醒，不代表采集后必须立即播放。尚未到提醒时间且需要未来新鲜数据确认的事项，会在后续轮询时重新验证；不以旧缓存预约长期危险播报。
7. 不变风险复用事件ID和播报版本，保留已播放次数；预警更新时更新原任务，升级可开启新一轮播报。明确解除、数据失效、城市或家庭计划改变后，旧任务不能继续领取。

依旧尊重免打扰、声音开关、重复间隔及最大次数。官方预警不受旧的早晨出门时窗限制，但不会擅自突破免打扰。没有和风天气凭据时继续保留旧的Open-Meteo晨间降温功能；已配置却暂时不可用时明确失败，不拼装虚假警报。模型不可用时不发布未经关联判断的新任务。

## 状态、审计与数据保留

- `GET /api/v1/companion/agent/weather`：管理员查看天气上下文及关联判断状态。
- 聊天请求的 `weather.future`：携带逐日、逐小时、官方预警及来源状态；访客的目的地只来自共享资料或自身可见计划。
- `GET /api/v1/devices/{id}/briefing?componentId=...`：取得可投递任务；沿用 `claim/result` 回执。
- `briefing_events` 保存系统生成的天气任务，`briefing_history`记录更新前内容，`briefing_claims`记录领取及播放结果。新增 `pig_weather_state` 保存城市提取与关联判断缓存。
- 不改写原有家庭资料、计划、API密钥、订阅来源、场景、手工信息列表或定时提示。自动天气任务属于系统新产生的数据，不混入用户手工创建的列表。

## 专项用例

| 编号 | 输入或操作 | 预期结果 |
|---|---|---|
| W01 | 新版8日/48小时/预警响应 | 时间、摄氏度、m/s、毫米正确，概率0–1转百分比，来源保留 |
| W02 | 同地点并发读取、经过5分钟 | 请求复用；只刷新预警，预报仍使用一小时缓存 |
| W03 | 上游断网，有旧缓存/无缓存 | 分别标记stale/unavailable，不泄漏凭据或原始错误URL |
| W04 | 空预警成功与连续失败 | 成功空数组为fresh，失败的短期缓存仍为unavailable |
| W05 | 更新、解除、过期预警混合 | 被替代及过期消息剔除，解除不当成危险事件 |
| W06 | 同名城市、附省份消歧 | 不静默选错城市，明确省份后正确定位 |
| W07 | 错误温度单位、无效时间 | 拒绝进入上下文与提醒判断 |
| W08 | 明日降温、通勤时段降雨及家庭路线 | 实际模型请求包含资料与天气；生成可领取的提前提醒，播放结果可追溯 |
| W09 | 重复轮询同一风险 | 不重复调用模型，不重建记录、不增加播报版本 |
| W10 | 同一官方预警升级且影响日期改变、随后解除 | 依据supersedes更新原ID；升级递增edition；解除后领取旧任务返回409 |
| W11 | 过期/未知天气 | 不生成新的主动提醒，不把缺失说成无预警 |
| W12 | 修改家庭记忆或取消行程 | 旧上下文生成的排队任务立即不可见，等待重新判断 |
| W13 | 免打扰、关闭组件天气功能、离开原早晨时窗 | 前两者阻止播报；新提前提醒不受旧时窗硬性限制 |
| W14 | 异地scope、日期不相交、伪造原文依据 | 不生成提醒 |
| W15 | 日常与旅行提前量 | 日常最多24小时、旅行最多72小时，不能无限提前 |
| W16 | 模型429或失败 | 不写伪造成功任务，不修改家庭资料 |
| W17 | 从记忆/计划提取城市及取消、过期计划 | 必须有原文依据，缓存复用；取消或过期的目的地不沿用 |
| W18 | 后台完整周期，旅行目的地预警 | 正确查询目的地、关联计划、投递对应屏幕 |
| W19 | 实际聊天消息 | `weather.future`含逐日、逐小时和预警状态，不只存在于后台缓存 |
| W20 | 风险内容改变且模型判断失败 | 撤下被替代的旧结论，不能继续播报旧预警级别或旧预报结论 |
| W21 | 同一城市的不同写法、多城市收到同一官方预警 | 按实际地点及官方消息编号去重，合并关联范围，不重复创建相同风险 |

## 执行与证据

确定性测试：

```powershell
node node_modules/jest/bin/jest.js --runInBand --forceExit --runTestsByPath tests/future-weather.test.js tests/weather-agent.test.js
```

真实接口与GLM验收：

```powershell
$env:PIG_CONTEXT_SNAPSHOT = 'C:\path\consistent-backup.db'
$env:PIG_CONTEXT_REPORT = 'C:\path\weather-evidence.json'
node tests/browser/weather-agent-live.js
```

脚本只打开一致性备份的临时副本。先读取真实城市、真实天气和真实家庭资料做判断，再用虚构家庭和天气场景验证GLM的通勤、旅行判断及投递生命周期。测试不会给真实屏幕投递测试预警，不写线上聊天或修改原始计划。来源和模型凭据在本机环境或副本配置中读取，不写入报告。

真实验证得到8个逐日时段、48个逐小时时段和2条官方预警。真实家庭资料在副本上生成了2条相关任务。7项端到端检查通过：真实天气API、真实家庭判断、GLM通勤与旅行关联、领取及回执、重复去重、取消行程、预警解除。首次合成场景在深夜要求马上收到通勤任务未通过；随后将验收时点明确设为出门前30分钟，验证临近出门的投递行为，避免把模型选择稍后提醒当成丢失。

脱敏证据见 [weather-advance-2026-11-08.json](test-results/weather-advance-2026-11-08.json)，其中的天气数值和预警仅代表采集时点。模拟场景的模型原始输出也保留，真实家庭资料全文和私人答复不进入报告。
